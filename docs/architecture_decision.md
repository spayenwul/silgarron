## ADR-001: LLM как Физический Движок (12 октября 2025)

### Контекст
Изначально LLM использовалась как "fallback" для создания красивого нарратива, а вся логика была в коде (HP, урон, броня). Однако концепция игры — "игрок может делать ЧТО УГОДНО" — требовала другого подхода.

### Проблема
Система на правилах (`pymorphy3` парсер) не могла обработать команды типа "опрокинуть стол на врага", "схватить за руку и вывернуть", "бросить песок в глаза". Каждый новый тип действия требовал новых правил.

### Решение
**Инвертировать роли: LLM как ядро, код как применитель.**

```
БЫЛО:
Code (правила) → LLM (косметика)

СТАЛО:
Code (парсинг) → LLM (физика) → Code (применение)
```

LLM получает команду и контекст, симулирует физические последствия, возвращает структурированный результат. Код только применяет эти эффекты.

### Последствия
**Плюсы:**
- ✅ Бесконечная вариативность действий
- ✅ Реалистичная физика без программирования каждого случая
- ✅ Масштабируемость

**Минусы:**
- ❌ Стоимость API (решается кэшированием)
- ❌ Задержка ответа (решается оптимизацией)
- ❌ Непредсказуемость LLM (решается валидацией)

### Статус
✅ Принято и реализуется

## ADR-002: Отказ от Двух Последовательных LLM-Вызовов (13 октября 2025)

### Контекст
Первоначальная идея: делать два вызова подряд.
1. Первый вызов: "Извлеки детали из команды"
2. Код выполняет расчёты
3. Второй вызов: "Опиши результат красиво"

### Проблема
**"Парадокс курицы и яйца":** Как LLM может получить данные для расчётов в первом запросе, если она сама должна сначала извлечь намерение, чтобы код понял, какие данные считать?

**Дублирование:** Два полных вызова API = двойная стоимость и задержка.

### Решение
**Function Calling Pattern** (Вызов Инструментов)

```
Запрос 1:
User: "Опрокидываю стол на врага"
LLM: {
  "function": "calculate_physics",
  "args": {
    "action": "push",
    "object": "table",
    "target": "enemy"
  }
}

→ Код выполняет расчёты →

Запрос 2:
User: (тот же контекст)
System: "Результат: стол весом 50кг, игрок толкнул с силой 200N..."
LLM: "Ваш мощный толчок опрокидывает массивный стол..."
```

Это всё ещё 2 вызова, но **в рамках одной сессии** с сохранением контекста.

### Последствия
**Плюсы:**
- ✅ Решает парадокс курицы и яйца
- ✅ LLM активно запрашивает нужные данные
- ✅ Код остаётся главным по части физики

**Минусы:**
- ⚠️ Всё ещё 2 вызова (но это неизбежно для сложных действий)

### Статус
✅ Принято, ожидает реализации в Sprint 2

## ADR-003: Трёхуровневая Маршрутизация Команд (14 октября 2025)

### Контекст
После решения использовать Function Calling возникла проблема стоимости: использовать этот мощный, но дорогой паттерн для КАЖДОЙ команды ("посмотреть инвентарь") неэффективно.

### Проблема
Нужна система приоритетов:
- Простые команды должны выполняться мгновенно и бесплатно
- Сложные — с полной мощью LLM

### Решение
┌─────────────────────────────────────────────────┐
│              FRONTEND (Browser)                 │
│  (UI Buttons + Text Input)                      │
└────┬────────────────────────────┬───────────────┘
     │ (UI Event)                 │ (Text Command)
     ↓                            ↓
┌────┴─────────────────┐ ┌────────────────────────┐
│ DIRECT CODE HANDLER  │ │   GAME LOGIC CORE      │
│ (e.g. show_inventory)│ │                        │
│ (No LLM, <10ms)       │ │  1. ROUTER (IntentService) │
└──────────────────────┘ │  (<50ms)                  │
                         │  "бью мечом" → COMPLEX   │
                         │  "осмотреться" → SIMPLE  │
                         │  └──────────┬───────────┘ │
                         │             ↓             │
                         │  2. DIRECTOR (Orchestrator)│
                         │  └──────┬──────────┬──────┘ │
                         │         ↓          ↓        │
                         │  ┌──────┴──────┐ ┌─┴───────────────┐ │
                         │  │ SIMPLE_LLM  │ │ COMPLEX_TOOL_CALL │ │
                         │  │ (1 call)    │ │ (2 calls + sim)   │ │
                         │  └─────────────┘ └───────────────────┘ │
                         └────────────────────────────────────────┘
**P5: Оптимизация по типу взаимодействия**

Не все действия требуют одинаковой обработки. Архитектура разделяет команды на три потока:

- **Системные команды (UI)**: Выполняются через UI-кнопки (инвентарь, карта, статистика). Обрабатываются **напрямую кодом**, без вызовов LLM. Мгновенно и бесплатно.

- **Нарративные команды (SIMPLE_LLM)**: Текстовый ввод, описывающий не-физические действия (осмотреться, поговорить, изучить). Обрабатываются **одним вызовом LLM** для генерации повествования. (~0.001₽, 500ms).

- **Физические команды (COMPLEX_TOOL_CALL)**: Текстовый ввод, описывающий **любое** действие с физическими последствиями (ударить мечом, опрокинуть стол, увернуться). Обрабатываются через **Function Calling** (два вызова LLM + вызов симулятора). (~0.002₽, 1500ms).

## ADR-004: IntentService как Fast Router, а не Detail Extractor (14 октября 2025)

### Контекст
`IntentService` был создан для извлечения деталей из команд (`pymorphy3` + правила). Однако тесты показали: он справляется с простыми случаями, но проваливается на сложных ("опрокинуть стол **из контекста** на врага **тоже из контекста**").

### Проблема
Пытаться улучшать парсер на правилах для бесконечной вариативности = бесконечная работа.

### Решение
**Изменить роль IntentService:**

```
БЫЛО (плохо):
IntentService → извлечь ВСЕ детали (action, weapon, target, modifiers...)

СТАЛО (хорошо):
IntentService → классифицировать ТИП команды (/SIMPLE/COMPLEX)
```

Его новая задача — супер-быстро (<50ms) определить, насколько сложная команда, не вникая в детали. Детали извлечёт LLM при необходимости.

### Последствия
**Плюсы:**
- ✅ IntentService делает то, что умеет отлично (классификация)
- ✅ LLM делает то, что умеет отлично (понимание контекста)
- ✅ 87% accuracy сохраняется

**Минусы:**
- Нет (это оптимальное разделение ответственности)

### Статус
✅ Принято, реализуется в Sprint 1

## ADR-005: Physical Simulation как Заглушки (10 января 2025)

### Контекст
Боевая система требует физической симуляции (траектория меча, кровопотеря, повреждение тканей). Но это сложная область, требующая отдельной команды.

### Проблема
Как продолжать разработку архитектуры, если физика ещё не готова?

### Решение
**Создать skeleton-реализацию:**
- `BodySystem`, `Wound`, `StatusEffect` — работающие классы
- Но логика внутри — заглушки (простые формулы)
- Интерфейсы стабильны → можно интегрировать параллельно

```python
class BodySystem:
    def apply_wound(self, wound):
        # TODO: Реальная физика кровопотери
        self.blood_volume -= 100  # Заглушка
```

### Последствия
**Плюсы:**
- ✅ Архитектура готова к интеграции
- ✅ Тесты проверяют интерфейсы
- ✅ Команды работают параллельно

**Минусы:**
- ⚠️ Игра не полностью реалистична (но это временно)

### Статус
✅ Реализовано в Phase 1, ожидает замены в Sprint 4

## ADR-006: Event Sourcing для Persistence (10 января 2025)

### Контекст
Нужна система сохранения/загрузки игры.

### Проблема
Традиционный подход (сериализация всего состояния) хрупок при изменениях кода.

### Решение
**Event Sourcing:**
- Сохраняем не состояние, а историю событий
- Состояние восстанавливается проигрыванием событий
- Формат: JSONL (одно событие = одна строка)

```jsonl
{"event": "game_started", "timestamp": "..."}
{"event": "player_moved", "from": "A", "to": "B"}
{"event": "combat_started", "enemies": ["goblin"]}
```

### Последствия
**Плюсы:**
- ✅ Устойчивость к изменениям кода
- ✅ Полная история игры (можно откатить)
- ✅ Лёгкая отладка (читаемый лог)

**Минусы:**
- ⚠️ Медленнее при загрузке (нужно проиграть все события)
  - Решение: периодические снапшоты

### Статус
✅ Реализовано в Phase 1

## ADR-008: Четкое разделение ответственности: UI vs Нарратив vs Физика (14 октября 2025)

### Контекст
В ходе реализации ADR-003 (Трёхуровневая Маршрутизация) возникла путаница в том, какие команды к какому уровню относятся. Изначально предполагалось, что "простая атака" может быть `SIMPLE_LLM`, а "опрокинуть стол" - `COMPLEX_TOOL_CALL`. Также была предпринята попытка обрабатывать системные команды ("инвентарь") через тот же текстовый парсер (`CODE_ONLY`).

### Проблема
1.  **Конфликт с TDD:** Идея "простой атаки" противоречила основному концепту (ADR-001), где **любое** физическое действие должно обрабатываться симулятором.
2.  **Нарративные коллизии:** Попытка парсить системные команды из текста приводила к ложным срабатываниям ("я нашел карту" → открывалось меню карты), что разрушало погружение.
3.  **Размытая граница:** Не было четкого критерия, что делает действие "простым" или "сложным" для классификатора, что приводило к ошибкам.

### Решение
**Окончательно определить и зафиксировать три НЕПЕРЕСЕКАЮЩИХСЯ потока команд:**

1.  **Системные команды (`CODE_ONLY`)**: Полностью **удалены** из текстового обработчика `IntentService`. Эти команды (инвентарь, карта, статистика) должны вызываться **только через элементы UI** (кнопки). Это гарантирует 100% точность и отсутствие нарративных коллизий.

2.  **Нарративные команды (`SIMPLE_LLM`)**: Используются для текстовых команд, которые **не требуют физической симуляции**. Их единственная цель — получить от LLM повествовательное описание. Примеры: "осмотреться", "поговорить с NPC", "изучить предмет".

3.  **Физические команды (`COMPLEX_TOOL_CALL`)**: Используются для **любой** текстовой команды, которая должна иметь **физические последствия в мире**, рассчитываемые через `PhysicalSimulator`. Сюда относятся **все боевые действия** (атака, блок, уворот) и все сложные взаимодействия с окружением (опрокинуть стол, перерубить веревку).

### Последствия
**Плюсы:**
- ✅ Архитектура стала кристально чистой и логичной.
- ✅ Полностью устранены нарративные коллизии.
- ✅ `IntentService` решает простую и четкую задачу: отличить нарратив от физики.
- ✅ Код `Director` и стратегий стал проще.

**Минусы:**
- ❌ Игрок не может *написать* "посмотреть инвентарь". Это осознанное проектное решение в пользу надежности.

### Статус
✅ Принято и реализовано в ходе Спринта 1.

## ADR-009: Централизованная Система Совместимости Биомов (15 октября 2025)

### Контекст

В проекте используется процедурная генерация мира с системой тегов и правилами совместимости биомов. Изначально эти правила были разбросаны по нескольким местам:
- `location_compatibility.yaml` содержал локальные правила `can_border`/`cannot_border` для каждого типа локации
- `tags_registry.yaml` содержал глобальные правила синергий и конфликтов между тегами
- Логика обработки была размазана между `SpatialLocationGenerator` и `HexWorldService`

Это приводило к дублированию логики и усложняло добавление новых правил совместимости.

### Проблема

1. **Дублирование данных**: Одни и те же несовместимости приходилось описывать в обоих файлах
2. **Сложность расширения**: Добавление нового правила требовало изменений в 3+ местах
3. **Отсутствие единого источника правды**: Не было ясно, какая система имеет приоритет
4. **Нет поддержки расового фактора**: Правила не учитывали, какая раса населяет локацию

### Решение

**Создать централизованный `CompatibilityService` как единую точку для всех проверок совместимости.**

#### Архитектура

```python
class CompatibilityService:
    def __init__(self, tags_registry: Dict):
        self.tags_registry = tags_registry  # Единый источник правил
        self._compatibility_cache = {}      # Кэширование результатов

    def calculate_biome_compatibility(
        self,
        biome_tags: List[str],
        neighbor_tags_list: List[List[str]]
    ) -> Dict:
        """Оценивает совместимость биома с его соседями"""
        # 1. Проверяет forbidden_combinations
        # 2. Вычисляет базовый score = 1.0
        # 3. Применяет synergies (увеличивают score)
        # 4. Применяет conflicts (уменьшают score)
        # 5. Возвращает score + детальный breakdown

    def find_best_biome_for_region(
        self,
        candidate_biomes: List[str],
        neighbor_biomes: List[str]
    ) -> Optional[str]:
        """Выбирает оптимальный биом из кандидатов"""
        # Сортирует по compatibility score, возвращает лучший

    def calculate_race_biome_score(
        self,
        race_tags: List[str],
        biome_tags: List[str]
    ) -> float:
        """Оценивает, насколько раса подходит для биома"""
        # Учитывает локальные preferred/forbidden расы
        # Применяет глобальные synergies/conflicts
```

#### Интеграция

```python
# api/game_session.py
class GameSession:
    def __init__(self, ...):
        # Сервис создаётся с YAML данными
        self.compatibility_service = CompatibilityService(
            tags_registry=world_data.get_tags_registry()
        )

# services/hex_world_service.py
class HexWorldService:
    @classmethod
    def from_dict(cls, data: Dict, compatibility_service: CompatibilityService):
        # Использует переданный сервис для проверок
        return cls(data, compatibility_service)
```

#### Приоритет данных

1. **Forbidden combinations** (tags_registry) → score = 0 (абсолютный запрет)
2. **Synergies** (tags_registry) → увеличивают score
3. **Conflicts** (tags_registry) → уменьшают score
4. **Local rules** (location_compatibility) → опциональный модификатор

### Последствия

**Плюсы:**
- ✅ **Единая точка истины**: Все правила в `tags_registry.yaml`
- ✅ **Кэширование**: Повторные проверки мгновенны
- ✅ **Тестируемость**: Можно тестировать изолированно от генерации
- ✅ **Расширяемость**: Легко добавлять новые типы правил
- ✅ **Прозрачность**: Детальный `breakdown` показывает, почему биом выбран
- ✅ **Модульность**: Сервис можно использовать отдельно от генерации

**Минусы:**
- ⚠️ **Рефакторинг**: Требуется обновить все места, где проверяется совместимость

## ADR-010: Гибридная Формула Совместимости (15 октября 2025)

### Контекст

После реализации централизованной системы совместимости (ADR-009) выявилась критическая проблема: **чисто мультипликативная формула** расчёта совместимости создаёт неконтролируемую систему балансировки.

Текущая реализация:
```python
score = 1.0
for tag_modifier in all_modifiers:
    score *= tag_modifier
# Итог: score = 1.0 * mod1 * mod2 * mod3 * ...
```

### Проблема

#### 1. Экспоненциальный рост

Добавление нового тега с бонусом `1.5` увеличивает score в 1.5 раза. При 10+ тегах это даёт неконтролируемый рост:

```yaml
# Пример
race: fen-kin
modifiers:
  ecology:toxic: 3.0
  surface:unstable: 2.0
  ecology:fertile: 0.5
  danger:environmental: 1.5

# Score: 1.0 * 3.0 * 2.0 * 0.5 * 1.5 = 4.5

# Добавляем ecology:wet: 2.0
# Score: 4.5 * 2.0 = 9.0 (в 2 раза!)
```

#### 2. Хрупкость

Изменение одного коэффициента полностью меняет результат:

```yaml
ecology:fertile: 0.5 → 0.1
# Score: 4.5 → 0.9 (в 5 раз меньше!)
```

#### 3. Непредсказуемость

С каждым новым тегом пространство возможных scores растёт экспоненциально. При 50 тегах балансировка становится невозможной.

#### 4. Проблема нуля

Если хотя бы один модификатор = `0.0`, весь score = `0.0`, даже если есть мощные бонусы от других тегов.

### Решение

**Hybrid Formula:** Сегментация модификаторов на три категории с разными правилами комбинирования.

#### Новая формула

```
Final Score = (Base Affinity + Situational Bonuses) * Multipliers

С ограничениями:
Final Score = clamp(result, min=0.0, max=5.0)
```

#### Компоненты

**1. Base Affinity (Базовое сродство) - Аддитивная часть**

Основные предпочтения расы. **Складывается**.

```yaml
base_affinity:
  ecology:toxic: +1.0      # Любят яды
  surface:unstable: +0.5   # Нравятся трясины
  ecology:fertile: -0.8    # Не любят плодородие
```

Диапазон: `[-2.0, +2.0]`
Стартовое значение: `1.0` (нейтральное)

**2. Multipliers (Мультипликаторы) - Мультипликативная часть**

Ключевые синергии для критических комбинаций. **Перемножается**.

```yaml
multipliers:
  - tags: [ecology:toxic, surface:unstable]
    factor: 1.5
    reason: "Идеальная ядовитая топь"
```

Диапазон: `[0.1, 2.0]`
Стартовое значение: `1.0` (нейтральное)
**Ограничение:** Максимум 5 мультипликаторов на расу!

**3. Situational Bonuses (Ситуативные бонусы) - Аддитивная часть**

Небольшие корректировки за второстепенные факторы. **Складывается**.

```yaml
situational_bonuses:
  danger:environmental: +0.2
  terrain:flat: +0.1
```

Диапазон: `[-0.5, +0.5]`
Стартовое значение: `0.0` (нет бонусов)

#### Алгоритм расчёта

```python
def calculate_race_biome_score_hybrid(race_data, biome_data):
    biome_tags = set(biome_data.get("tags", []))

    # 1. Base Affinity
    base_score = 1.0
    for tag, value in race_data.get("base_affinity", {}).items():
        if tag in biome_tags:
            base_score += value

    # 2. Situational Bonuses
    situational_score = 0.0
    for tag, value in race_data.get("situational_bonuses", {}).items():
        if tag in biome_tags:
            situational_score += value

    # 3. Multipliers
    total_multiplier = 1.0
    for rule in race_data.get("multipliers", []):
        if set(rule["tags"]).issubset(biome_tags):
            total_multiplier *= rule["factor"]

    # 4. Комбинируем
    combined = (base_score + situational_score) * total_multiplier

    # 5. Границы
    return max(0.0, min(5.0, combined))
```

### Примеры

#### Пример 1: Идеальный биом

```yaml

  ecology:toxic: +1.0
  surface:unstable: +0.5
multipliers:
  - tags: [ecology:toxic, surface:unstable]
    factor: 1.5

  danger:environmental: +0.2

# Биом: toxic_swamp

# Расчёт:

Situational: 0.0 + 0.2 = 0.2
Additive:    2.5 + 0.2 = 2.7
Multiplier:  1.0 * 1.5 = 1.5
Final:       2.7 * 1.5 = 4.05
```

#### Пример 2: Нейтральный биом

```yaml

# Расчёт:

Situational: 0.0
Multiplier:  1.0
Final:       1.0
```

### Последствия

**Плюсы:**

✅ **Предсказуемость:** Добавление тега `+0.3` даёт прогнозируемый рост на `0.3`, а не в 1.3 раза

✅ **Контролируемость:** Мультипликаторы только для 3-5 ключевых синергий

✅ **Масштабируемость:** Добавление 50 новых тегов не ломает баланс

✅ **Понятность:** YAML читается как естественный язык ("Раса любит токсичность +1.0")

✅ **Отлаживаемость:** Легко понять, откуда берётся каждое значение score

**Минусы:**

⚠️ **Миграция данных:** Требуется конвертировать все существующие правила совместимости

⚠️ **Рефакторинг кода:** Изменить логику в `CompatibilityService`

⚠️ **Обновление тестов:** 19 unit-тестов нужно адаптировать под новую формулу

**Trade-offs:**

- Более сложная структура данных (3 секции вместо 1), но зато каждая секция интуитивно понятна

### План миграции

2. **Конвертация данных:** Преобразовать старые правила по эвристике:

   - `mod <= 0.5` → base_affinity с сильным отрицательным или multiplier

## ADR-011: Переход на единую глобальную hex-карту (20 октября 2025)

### Контекст
Текущая система использует "регионы-контейнеры" с локальными биомами.
Это создаёт фундаментальные проблемы:

**Технические:**
- Горы не выглядят как горы, а как абстрактные узлы графа
- Невозможно проложить маршрут каравана между локациями
- Границы биомов произвольны и не следуют географической логике

**Нарративные:**
- AI-нарратор не может описать "Склеритовый хребет" как непрерывную горную цепь
- События не распространяются естественно (пожар, эпидемия)
- Фракции не имеют географически логичных границ

### Проблема
Как создать живой, взаимосвязанный мир, где география определяет логику повествования?

### Рассмотренные решения

**Вариант A: Оставить текущую систему регионов-контейнеров**
- ➕ Не требует переработки
- ➖ Не решает фундаментальных проблем
- ➖ Ограничивает возможности AI-нарратора
- **Решение:** Отклонено

**Вариант B: Гибридная система (регионы + глобальная сетка)**
- ➕ Постепенная миграция возможна
- ➖ Усложняет архитектуру (два параллельных подхода)
- ➖ Трудно поддерживать консистентность
- **Решение:** Отклонено из-за сложности

**Вариант C: Полный переход на двухуровневую систему (Global + Local)**
- ➕ Чистая, понятная архитектура
- ➕ Географическая консистентность
- ➕ Естественные формы регионов и биомов
- ➕ Pathfinding, миграция, распространение событий
- ➖ Требует переработки генерации (2-3 недели работы)
- **Решение:** ✅ Принято

### Решение

**Ввести двухуровневую систему генерации мира:**

#### Level 0: Global Map
- Единая hex-сетка **256x256 секторов**
- Каждый сектор имеет физические свойства (высота, температура, влажность)
- Биом рассчитывается из физических свойств
- Генерация через Perlin noise + климатические правила
- **Seed-based:** воспроизводимая генерация

#### Level 1: Locations (POI)
- Детальные карты 20x20 для "точек интереса"
- Загружаются по требованию (не каждый сектор = локация)
- Используют существующий `HexGridService`
- Контекст от глобальной карты (биом) влияет на детальную генерацию

### Последствия

**Плюсы:**
- ✅ Географическая консистентность
- ✅ Естественные формы регионов (горные хребты, речные долины)
- ✅ Pathfinding для NPC/караванов по единой сетке
- ✅ Возможность моделировать миграцию животных, распространение болезней
- ✅ AI-нарратор может создавать истории, связанные с географией
- ✅ Не каждый сектор = детальная локация → экономия ресурсов
- ✅ Seed-based → повторяемость, шаринг миров, отладка

**Минусы:**
- ❌ Требует 2-3 недели разработки (Sprint 2-3)
- ❌ Нужно рефакторить `HexWorldService`
- ❌ Увеличение памяти для хранения глобальной карты (~2-3 MB)
- ❌ Миграция старых сохранений потребует усилий

**Технические риски:**
- ⚠️ Производительность pathfinding на карте 256x256
  - **Митигация:** A* с эвристикой, кэширование путей
- ⚠️ Perlin noise может создавать "шумные" ландшафты
  - **Митигация:** Tuning octaves, сглаживание

### Альтернативные подходы (отклонены)
1. **Огромный мир 1000x1000:** Отклонено - слишком много пустого пространства, низкая нарративная плотность
2. **Процедурная генерация каждый раз:** Отклонено - нарушает постоянство мира, нельзя сохранить изменения

### Статус
✅ Принято 20 октября 2025

## ADR-012: Размер глобальной карты и стратегия генерации (20 октября 2025)

### Контекст
После принятия решения о единой глобальной hex-карте (ADR-011),
необходимо определить:
1. Размер карты (100x100? 256x256? 1000x1000?)
2. Тип генерации (процедурная каждый раз или фиксированная с seed?)

Это критичные решения, влияющие на производительность, геймплей и нарратив.

### Проблема
**Вопрос 1:** Какой размер карты обеспечит баланс между масштабом и нарративной плотностью?

**Вопрос 2:** Как генерировать мир - заново каждый раз или один раз с сохранением изменений?

### Анализ размера карты

**100x100 хексов** (~10,000 секторов)
- ➕ Быстрая генерация (<5 сек)
- ➕ Хорошая производительность pathfinding
- ➖ Слишком мал для ощущения масштаба
- ➖ Ограниченное пространство для фракций
- **Вывод:** Слишком мало для эпического мира

**1000x1000 хексов** (~1,000,000 секторов)
- ➕ Огромный мир
- ➖ Очень медленная генерация (>60 сек)
- ➖ Pathfinding становится проблемой
- ➖ **КРИТИЧНО:** Низкая нарративная плотность
  - Сотни пустых хексов между POI
  - AI-нарратору нечего описывать
  - Путешествие = скучная механика ("вы продолжаете идти...")
- **Вывод:** Слишком большой для текстовой RPG

**256x256 хексов** (~65,000 секторов)
- ➕ Достаточно большой для нескольких континентов
- ➕ Генерация за <30 секунд
- ➕ Pathfinding управляем (с оптимизацией)
- ➕ **КРИТИЧНО:** Оптимальная нарративная плотность
  - Плотность: 1 POI на каждые 50-100 секторов
  - ~650-1300 интересных локаций
  - Каждый переход игрока потенциально значим
- ➕ Фракции имеют общие границы → конфликты
- ➕ Караванные пути пересекаются → торговля → истории
- **Вывод:** Идеальный баланс ✅

### Анализ типа генерации

**Процедурная (генерация каждый раз заново)**

➕ Бесконечная вариативность
➖ КРИТИЧНО: Нарушает постоянство мира

Игрок не может запоминать дорогу
AI-нарратор не может строить долгосрочные сюжеты
Невозможно сохранить изменения (сожжённый лес, разрушенная деревня)


➖ Невозможность отладки (каждый раз новый баг)
➖ Нельзя делиться интересными мирами
Вывод: Неприемлемо для сюжетной RPG

Фиксированная с seed (генерация 1 раз)

➕ КРИТИЧНО: Постоянство и логика мира

Один seed → один воспроизводимый мир
Игрок запоминает географию, строит стратегию
AI-нарратор строит долгосрочные сюжеты


➕ Динамические изменения сохраняются

Игрок сжигает лес → лес остаётся сгоревшим
AI добавляет новый лагерь гоблинов → он постоянен


➕ Повторяемость для отладки
➕ Возможность шаринга seed'ов между игроками
➕ Эффективное сохранение: initial_state.json + delta.json
➖ Требует больше места для хранения (~2-3 MB на мир)
Вывод: Идеально для нашей игры ✅

Решение
Размер карты: 256x256 хексов
```yaml# config/world_generation.yaml
global_map:
  default_width: 256
  default_height: 256
  hex_size: 100.0
Обоснование:
```
Для текстовой RPG с AI-нарратором нарративная плотность важнее физического размера.
256x256 - это "золотая середина":

Достаточно большой для континентов и эпического масштаба
Достаточно компактный для связности (фракции соприкасаются)
Идеален для плотности (~650+ POI, каждый переход значим)


Тип генерации: Seed-based фиксированная

## ADR-013: Анатомическая генерация живого мира (21 октября 2025)

### Контекст

После принятия решения о глобальной hex-карте (ADR-011, ADR-012) началась разработка Sprint 3.5 - генератора глобальной карты. Изначально был создан план генерации, основанный на **стандартном подходе процедурной генерации миров**:

```
Perlin noise → Континенты → Климатические зоны → Биомы
(геология, тектоника, эрозия)
```

Однако этот подход **фундаментально противоречит уникальной природе мира Silgarron**.

### Проблема

**Сильгаррон - это НЕ планета. Это ЖИВОЕ СУЩЕСТВО (биопанк-организм).**

Применение стандартной геологической генерации создаёт концептуальную несовместимость:

1. **Геологические концепции не подходят:**
   - Нет "климата" - есть **метаболическое тепло** (активность тканей)
   - Нет "рек" - есть **лимфотоки** (кровеносная система)
   - Нет "гор" - есть **костяной хребет** (позвоночник существа)
   - Нет "океана" - есть **первичная жидкость** (протоплазменный океан)

2. **Игнорируется ключевая механика "Дыхание":**
   - Весь мир участвует в циклическом расширении/сжатии
   - Воздух втягивается в **Альвеолярные каверны** (лёгкие мира)
   - Создаются воздушные потоки, влияющие на влажность

3. **Биомы - это НЕ климатические зоны:**
   - Это **типы тканей** живого организма
   - Дерма (кожа), мышцы, хитин, кость, лимфа
   - Распределяются по **физиологической логике**, а не географической

4. **AI-нарратор не может создавать биопанк-описания:**
   - "Вы идёте по горам" → ❌ Геологическое описание
   - "Вы ступаете по позвонкам Костяного хребта, хрустящим под ногами" → ✅ Анатомическое описание

### Решение

**Полностью переработать концепцию генерации мира: симулировать анатомию, а не геологию.**

#### Новая философия генерации: "От скелета к коже"

```
1. СКЕЛЕТ (Skeleton)
   ├─ Генерация Костяного Хребта (ridge-biased noise)
   └─ Определение крупных костных структур

2. КРОВЕНОСНАЯ СИСТЕМА (Circulatory System)
   ├─ Размещение "сердец" (истоков лимфотоков)
   ├─ Flow Accumulation для русел
   └─ Лимфатическая сеть (артерии → капилляры)

3. ДЫХАТЕЛЬНАЯ СИСТЕМА (Respiratory System)
   ├─ Размещение Альвеолярных каверн ("лёгких")
   ├─ BFS для воздушных потоков
   └─ Карта интенсивности "вдоха"

4. МЕТАБОЛИЗМ (Metabolism)
   ├─ Расчёт активности тканей
   ├─ Температурная карта (не климат, а жизнедеятельность)
   └─ Распределение ресурсов

5. ТКАНИ (Tissues)
   ├─ Назначение типов тканей на основе всех слоёв
   ├─ Система приоритетов
   └─ Плавные переходы (мембрана → мышцы → кость)

6. ДИНАМИКА ("Дыхание" и пульсация)
   ├─ Фазы дыхательного цикла
   └─ Стабильные vs динамические зоны
```

#### Ключевые технические изменения

**1. Ridge-biased Perlin Noise для органической структуры:**

Вместо случайного шума создаём **доминирующий хребет** (позвоночник) с ответвлениями ("рёбра"):

```python
def _generate_skeletal_structure(self) -> np.ndarray:
    # Базовый Perlin noise (микрорельеф)
    base_noise = generate_perlin(...)

    # Создание "позвоночника" (ridge mask)
    spine_bias = self._create_spine_mask()

    # Создание "рёбер" (ответвлений)
    rib_bias = self._create_rib_mask()

    # Комбинация: 60% шум + 30% хребет + 10% рёбра
    structural_map = base_noise * 0.6 + spine_bias * 0.3 + rib_bias * 0.1
```

**2. D8 Flow Accumulation для лимфатической системы:**

Лимфотоки текут **по законам физиологии**, а не эрозии:

```python
def _generate_lymphatic_system(self, structure_map):
    # Истоки в возвышенных зонах (фильтрующие органы)
    sources = self._find_lymph_sources(structure_map)

    # D8 Flow Accumulation для симуляции потоков
    flow_accumulation = self._calculate_flow_accumulation(structure_map, sources)

    # Лимфоток там, где накопление превышает порог
    lymph_network_map = flow_accumulation > threshold
```

**3. BFS для "Дыхания" мира:**

Альвеолярные каверны втягивают воздух, создавая **зоны высушивания**:

```python
def _generate_respiratory_system(self, structure_map):
    # Разместить Альвеолярные каверны (входы в "лёгкие")
    caverns = self._place_alveolar_caverns(structure_map)

    # BFS для расчёта воздушных потоков
    airflow_map = self._calculate_airflow_to_caverns(caverns)

    # Высокий airflow → низкая влажность
    desiccation_map = airflow_map.copy()
```

**4. Метаболическое тепло вместо климата:**

Температура = активность тканей, а не широта:

```python
def _generate_metabolic_activity(self, structure_map, lymph_network):
    # Хребет (кость) холодный
    if elevation > 0.7:
        temp -= (elevation - 0.7) * 40  # До -12°C

    # Лимфотоки тёплые (активная циркуляция)
    temp += lymph_intensity * 15  # До +15°C

    # Низины (активные ткани) умеренно тёплые
    if elevation < 0.4:
        temp += (0.4 - elevation) * 10  # До +4°C
```

**5. tissue_rules.yaml вместо biome_rules.yaml:**

```yaml
tissues:
  osseous_ridge:
    name: "Костяной хребет"
    priority: 50
    structural_elevation: [0.7, 1.0]

  pulsating_dermis:
    name: "Пульсирующая дерма"
    priority: 12

```

**6. Расширенная модель GlobalSector:**

```python
@dataclass
class GlobalSector:
    coord: HexCoord

    # Физические свойства
    elevation: float
    temperature: float
    moisture: float
    biome_type: str  # Теперь это "тип ткани"

    metabolic_heat: float  # Активность тканей

```

**7. Медицинское сканирование (визуализация):**

Вместо географической карты создаём **анатомическую визуализацию** с 5 слоями:

1. **Structural Anatomy** - костяная структура (cmap='bone')
2. **Tissue Morphology** - типы тканей (анатомические цвета)
3. **Metabolic Heatmap** - активность тканей (cmap='afmhot')
4. **Fluid Saturation** - насыщенность лимфой (cmap='viridis')
5. **Airflow Map** - интенсивность дыхания (cmap='cool')

### Последствия

**Плюсы:**

✅ **Концептуальная консистентность:** Генерация полностью соответствует биопанк-природе мира

✅ **Уникальность:** Ни одна другая RPG не имеет подобной системы генерации

✅ **Богатый нарратив:** AI-нарратор может создавать уникальные описания:
   - "Вы ступаете по пульсирующей дерме, чувствуя, как мир вдыхает"
   - "Золотистая лимфа течёт по каналам, пульсируя в такт сердцебиению мира"
   - "Костяной хребет вздымается перед вами, белые позвонки протыкают небо"

✅ **Механическая глубина:** "Дыхание" создаёт динамические зоны влажности/сухости

✅ **Биологическая логичность:**
   - Хребет холодный (мёртвая кость)
   - Лимфотоки тёплые (активная циркуляция)
   - Высокий airflow → низкая влажность

✅ **Модульность:** Каждая система (скелет, кровь, дыхание) - отдельный модуль

**Минусы:**

❌ **Сложность реализации:** Требуется реализовать 6 взаимосвязанных систем (44-50 часов работы)

❌ **Нестандартность:** Нет готовых библиотек для "генерации живого организма"

❌ **Балансировка:** Требуется тщательный тюнинг параметров для правдоподобности

❌ **Обучение команды:** Разработчики должны понять физиологическую логику вместо геологической

**Trade-offs:**

- Жертвуем привычной геологической генерацией ради уникальности и концептуальной консистентности
- Более сложная реализация, но результат полностью соответствует видению проекта

### Сравнение подходов

| Аспект | Геологическая генерация | Анатомическая генерация |
|--------|------------------------|------------------------|
| **Высота** | Perlin noise → горы/равнины | Ridge-biased noise → позвоночник + мягкие ткани |
| **Температура** | Широта (экватор/полюс) | Метаболическое тепло (активность тканей) |

| **Биомы** | Климатические зоны | Типы тканей (дерма, хитин, кость, лимфа) |
| **Реки** | Эрозия | Лимфотоки (кровь мира) |
| **AI-нарратив** | Стандартные описания | Уникальные биопанк-описания |

## ADR-014: Механика "Дыхания" - Выдох вместо Вдоха (23 октября 2025)

### Контекст

После создания технического плана Sprint 3.5 (анатомическая генерация мира) была выявлена **фундаментальная концептуальная ошибка** в реализации системы "Дыхания" мира.

**Что в техническом плане (Sprint 3.5 v2.1):**
- Задача 1.4 реализует механику **"Вдох"**: "Воздух втягивается в Альвеолярные каверны"
- Алгоритм: BFS от каверн с затухающей интенсивностью (`intensity * 0.95`)
- Эффект: `desiccation` (высушивание) вокруг каверн
- Семантика: Каверны = **СТОКИ** (поглощающие центры)

**Что в лоре (`docs/lore/Общее.md`):**
- Мир находится в фазе **позднего ВЫДОХА**: "Сильгаррон медленно выдыхает, насыщая атмосферу биоактивными газами и спорами"
- Последствия Выдоха:
  - Высокое давление (в 1.5-2 раза выше земного)
  - Плотный, тяжелый воздух
  - Насыщение атмосферы спорами (Биолюм)
  - Невозможность полётов
- Семантика: Каверны = **ИСТОЧНИКИ** (излучающие центры)

### Проблема

**Как реализовать дыхательную систему мира так, чтобы она соответствовала лору (фаза Выдоха), но при этом использовала работающий алгоритм BFS?**

Несоответствие создаёт:
1. **Логическое противоречие:** В мире с плотной, влажной атмосферой не может быть "зон высушивания" вокруг каверн
2. **Нарративный диссонанс:** AI-нарратор не сможет описывать "споровые туманы", если генератор создаёт "сухие ветра"
3. **Технический долг:** Все будущие механики (погода, магия, существа) строятся на неверной основе

### Рассмотренные альтернативы

**Вариант A: Изменить лор (принять фазу Вдоха)**
- ➕ Не требует изменений в техническом плане
- ➖ Отбрасывает ключевую концепцию "Эпохи Давления" из лора
- ➖ Обедняет уникальность мира (от "дышащего титана" к "всасывающей воронке")
- ➖ Требует переписать несколько документов лора
- **Решение:** Отклонено (творчески слабое решение)

**Вариант B: Полная переделка алгоритма (симуляция потоков наружу)**
- ➕ "Честная" физическая симуляция выдоха
- ➖ Колоссальное усложнение (вместо простого BFS - сложная гидродинамика)
- ➖ Риск увязнуть в технических деталях
- ➖ Результат визуально может быть неотличим от варианта C
- **Решение:** Отклонено (overengineering для Sprint 3.5)

**Вариант C: Переименовать и переосмыслить (рекомендуемый)**
- ➕ Сохраняет работающий алгоритм BFS
- ➕ Минимальные изменения кода (косметические + одна функция)
- ➕ Полное соответствие лору
- ➕ Более интересный мир (споровые туманы вместо сухих зон)
- ➖ Требует пересмотр семантики переменных
- **Решение:** ✅ Принято

### Решение

**Принять "Вариант C: Переименовать и переосмыслить"**

Алгоритм BFS универсален - он создаёт **градиент влияния от источников**. Этот градиент может моделировать как "силу всасывания" (Вдох), так и "концентрацию исходящего вещества" (Выдох).

#### Ключевые изменения:

**1. Переименование переменных и полей:**

```python
# БЫЛО (концепция Вдоха):
airflow_intensity      → exhalation_influence
desiccation           → bioactive_saturation
vent_attractor_coord  → nearest_cavern_coord

# СТАЛО (концепция Выдоха):
exhalation_influence  # Концентрация выдыхаемых спор/газов
bioactive_saturation  # Насыщенность биоактивными веществами
nearest_cavern_coord  # Ближайшая каверна (нейтральное название)
```

**2. Изменение функции эффекта:**

```python
# БЫЛО:
def _calculate_desiccation_effect(self, airflow_map):
    """Высокий airflow → высокая сухость"""
    return airflow_map.copy()

# СТАЛО:
def _calculate_bioactive_effect(self, exhalation_map):
    """
    Высокая концентрация выдоха → токсичность, споровые туманы, мутации.

    Используется в _select_tissue для назначения:
    - necrotic_tissue (некротические топи)
    - spore_choked_thicket (споровые заросли)
    - mutated_dermis (мутировавшая дерма)
    """
    bioactive_map = exhalation_map.copy()
    return bioactive_map
```

### Технические детали реализации

**Алгоритм остаётся тем же (BFS с затуханием):**

```python
def _calculate_exhalation_influence(self, caverns: List[Tuple[int, int]]) -> np.ndarray:
    """
    BFS от каверн для расчёта концентрации выдыхаемых веществ.

    Логика:
    - Каверны = источники (концентрация 1.0)
    - Каждый шаг от каверны: концентрация *= decay_rate (0.95)
    - Результат: градиент от 1.0 (у каверны) до ~0.0 (вдали)
    """
    exhalation_map = np.zeros((self.height, self.width))
    queue = deque()

    # Инициализация: каверны - источники
    for cavern in caverns:
        exhalation_map[cavern] = 1.0
        queue.append((cavern, 1.0))

    decay_rate = 0.95
    visited = set(caverns)

    while queue:
        (x, y), intensity = queue.popleft()

        for dx, dy in [(-1,0), (1,0), (0,-1), (0,1)]:
            nx, ny = x + dx, y + dy
            if 0 <= nx < self.height and 0 <= ny < self.width:
                if (nx, ny) not in visited:
                    new_intensity = intensity * decay_rate
                    if new_intensity > 0.05:  # Порог отсечения
                        exhalation_map[nx, ny] = new_intensity
                        queue.append(((nx, ny), new_intensity))
                        visited.add((nx, ny))

    return exhalation_map
```

**Интерпретация результата:**

- `exhalation_influence = 1.0` → Прямо у каверны (максимальная концентрация спор)
- `exhalation_influence = 0.7` → Зона споровых туманов
- `exhalation_influence = 0.3` → Умеренное влияние (лёгкая дымка)
- `exhalation_influence = 0.0` → Вдали от каверн (чистый воздух)

## ADR-015: Гибридная система гексагональных координат (23 октября 2025)

### Контекст

После принятия решения о глобальной hex-карте (ADR-011, ADR-012, ADR-013) и анатомической генерации мира возник вопрос выбора системы координат для гексагональной сетки.

**Ключевой источник информации:** [Red Blob Games - Hexagonal Grids](https://www.redblobgames.com/grids/hexagons/)

Существует несколько подходов к представлению гексагональных координат, каждый со своими преимуществами и недостатками.

### Проблема

Выбор системы координат — это не просто техническое решение. Это **глубоко тематический выбор**, который должен поддерживать саму суть Сильгаррона как **мира-организма** с четкой анатомической структурой.

**Ключевой вопрос:** Какая система координат лучше всего рассказывает историю Сильгаррона и его анатомии?

### Рассмотренные альтернативы

#### Вариант A: Offset Coordinates - Horizontal Layout (Flat Top)

**Описание:** Гексагоны с плоским верхом, ряды идут ровно по горизонтали.

**Применимость к Сильгаррону:**
- ➕ Привычный вид для классических карт континентов
- ➖ **Критический недостаток:** Не подходит для анатомии Сильгаррона
- ➖ Размывает вертикальную ось **Склеритового Хребта** (позвоночник мира)
- ➖ Горизонтальная ориентация создает ощущение "геологического" мира, а не "анатомического"
- ➖ Противоречит идее вертикального "позвоночника" как центральной оси

**Решение:** ❌ Отклонено (не соответствует анатомической концепции)

#### Вариант B: Offset Coordinates - Vertical Layout (Pointy Top)

**Описание:** Гексагоны с острым верхом, столбцы идут ровно по вертикали.

**Применимость к Сильгаррону:**
- ➕ **Тематическое соответствие:** Визуально усиливает **Склеритовый Хребет** как центральную вертикальную ось
- ➕ **Анатомическая аналогия:** Карта похожа на анатомический чертеж, рассматриваемый сверху вниз
- ➕ **Органические потоки:** Лимфотоки (реки) естественно "стекают" по диагонали от Хребта
- ➕ **Интуитивность:** Простота для игроков ("иди на три гекса на север по хребту")
- ➕ **Нарративная сила:** AI-нарратор может описывать мир вдоль "позвоночника"
- ➖ Математически менее элегантен для некоторых расчетов расстояния

**Решение:** ✅ **Принято для визуального представления**

#### Вариант C: Axial/Cube Coordinates

**Описание:** Математически элегантная система, основанная на трех осях под 120°. Визуально сетка выглядит так же, как Offset, но внутренняя логика другая.

**Применимость к Сильгаррону:**
- ➕ **Механическая элегантность:** Идеальна для расчетов расстояний, области видимости, распространения эффектов
- ➕ **Тематическое соответствие (глубокое):** Три сбалансированные оси (`x + y + z = 0`) — **метафора Сильгаррона как единой, взаимосвязанной системы**
- ➕ **Органическое распространение:** Алгоритмы дают идеально ровные, органичные круги (пожары, эпидемии, заражение от Новых Богов)
- ➕ **Отсутствие "швов":** Нет аномалий и краевых эффектов, характерных для Offset-систем
- ➖ Менее интуитивна для новичков (требует понимания 3D координат)
- ➖ Преобразование в экранные координаты требует дополнительного шага

**Решение:** ✅ **Принято для внутренней механики**

### Решение

**Гибридный подход: Использовать обе системы для разных целей.**

#### 1. Визуальное представление (для игроков и нарратива):

**Вертикальная Offset-система ("Pointy Top")**

```python
# Внешний вид карты для игроков
class HexGridRenderer:
    orientation = "pointy_top"  # Вертикальные столбцы
    # Визуализация подчеркивает "позвоночник" (Склеритовый Хребет)
```

**Почему:**
- Интуитивно понятна игрокам
- Идеально отражает анатомию Сильгаррона с центральным "позвоночником"
- Лучше всего для описания и навигации ("север-юг вдоль хребта")
- AI-нарратор естественно описывает движение вдоль вертикальной оси

#### 2. Внутренняя механика (для расчетов):

**Cube Coordinates (Кубическая система)**

```python
# Внутреннее представление для логики
@dataclass
class HexCoord:
    q: int  # Axial coordinate
    r: int  # Axial coordinate

    @property
    def s(self) -> int:
        """Cube coordinate (derived): q + r + s = 0"""
        return -self.q - self.r

    def distance_to(self, other: 'HexCoord') -> int:
        """Идеально точное расстояние через cube coords"""
        return (abs(self.q - other.q) +
                abs(self.r - other.r) +
                abs(self.s - other.s)) // 2
```

**Почему:**
- Отражает глубокую взаимосвязанную природу мира-организма
- Идеальна для расчетов:
  - Расстояния (distance)
  - Движение (pathfinding)
  - Область видимости (field of view)
  - Распространение органических явлений (болезни, рост, "язвы" Новых Богов)

#### 3. Преобразование координат:

Red Blob Games предоставляет формулы для мгновенного преобразования между системами:

```python
class CoordinateConverter:
    @staticmethod
    def offset_to_axial(col: int, row: int) -> Tuple[int, int]:
        """Pointy-top offset → axial"""
        q = col
        r = row - (col - (col & 1)) // 2
        return q, r

    @staticmethod
    def axial_to_offset(q: int, r: int) -> Tuple[int, int]:
        """Axial → pointy-top offset"""
        col = q
        row = r + (q - (q & 1)) // 2
        return col, row
```

### Последствия

**Плюсы:**

✅ **Лучшее из двух миров:**
- Интуитивная визуализация (Offset Pointy Top)
- Элегантная математика (Cube Coordinates)

✅ **Тематическое соответствие:**
- Визуально подчеркивает анатомию (вертикальный позвоночник)
- Математически отражает единство организма (3 сбалансированные оси)

✅ **Нарративная сила:**
- AI-нарратор описывает движение вдоль "позвоночника"
- "Вы поднимаетесь на север по Склеритовому Хребту"

✅ **Механическая мощность:**
- Распространение "Кристаллической Скверны" — идеальные органичные круги
- Pathfinding для караванов — быстрый A*
- Миграция животных — естественные потоки

✅ **Масштабируемость:**
- Преобразование координат О(1) — мгновенное
- Готовность к будущим механикам (магия, погода, события)

**Минусы:**

❌ **Дополнительная сложность:**
- Требуется слой преобразования координат
- Разработчики должны понимать обе системы

❌ **Потенциальные баги:**
- Риск ошибок при преобразовании координат

**Trade-offs:**

- Жертвуем простотой "одной системы" ради тематического соответствия и механической элегантности
- Дополнительная сложность оправдана уникальностью мира и качеством игрового опыта

### Технические детали

#### Структура данных:

```python
# models/hex_coord.py
@dataclass
class HexCoord:
    """
    Гексагональные координаты (Axial + Cube).

    Хранит: axial (q, r)
    Вычисляет: cube (q, r, s где s = -q - r)
    Преобразует: offset (col, row) через конвертер
    """
    q: int  # Axial q
    r: int  # Axial r

    @property
    def s(self) -> int:
        """Cube s coordinate: q + r + s = 0"""
        return -self.q - self.r

    def to_offset_pointy(self) -> Tuple[int, int]:
        """Конвертация в Offset Pointy Top для рендеринга"""
        col = self.q
        row = self.r + (self.q - (self.q & 1)) // 2
        return col, row

    @classmethod
    def from_offset_pointy(cls, col: int, row: int) -> 'HexCoord':
        """Создание из Offset Pointy Top координат"""
        q = col
        r = row - (col - (col & 1)) // 2
        return cls(q, r)

    def distance_to(self, other: 'HexCoord') -> int:
        """Манхэттенское расстояние в cube coordinates"""
        return (abs(self.q - other.q) +
                abs(self.r - other.r) +
                abs(self.s - other.s)) // 2

    def neighbors(self) -> List['HexCoord']:
        """Возвращает 6 соседних гексов"""
        directions = [
            (1, 0), (1, -1), (0, -1),
            (-1, 0), (-1, 1), (0, 1)
        ]
        return [HexCoord(self.q + dq, self.r + dr)
                for dq, dr in directions]
```

### Философия дизайна

> **"Форма следует за функцией, но форма также рассказывает историю"**
>
> Вертикальная ориентация гексагональной сетки (Pointy Top) — это не случайный выбор. Это **визуальное воплощение анатомии Сильгаррона**. Каждый раз, когда игрок смотрит на карту, он видит не абстрактную сетку, а **позвоночник живого существа**, протянувшийся с севера на юг.
>
> Но красивая визуализация должна опираться на прочный математический фундамент. Cube coordinates — это не просто "удобная формула". Это **метафора единства мира**: три оси, связанные уравнением `x + y + z = 0`, отражают глубокую взаимосвязанность всех частей Сильгаррона.
>
> Гибридный подход — это признание того, что **разные уровни системы служат разным целям**: визуализация служит нарративу, математика служит симуляции, и обе служат созданию живого, правдоподобного мира.

Как хранить состояние игры так, чтобы обеспечить быструю загрузку,

### Рассмотренные альтернативы

- ➕ Стандартная реляционная БД
- ➕ Встроена в Python
- ➖ Сложность схемы для иерархических данных
- ➖ Миграции схемы при изменениях кода

- ➕ Возможность отката

- Каждое событие = одна строка JSON
- Состояние восстанавливается проигрыванием событий
- Периодические снапшоты для ускорения загрузки

- ✅ Возможность откатов

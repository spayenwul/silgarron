## 🎯 Философия Документации

**Документация — это не бремя, а инструмент.**

Хорошая документация:
- ✅ Экономит время (не нужно вспоминать, "почему мы так сделали")
- ✅ Помогает онбордингу (новый разработчик быстро вникает)
- ✅ Служит чек-листом (что сделано, что осталось)
- ✅ Фиксирует решения (ADR предотвращает "хождение по кругу")

Плохая документация:
- ❌ Устаревшая (говорит одно, код делает другое)
- ❌ Избыточная (никто не читает 100-страничные доки)
- ❌ Хаотичная (информация в 10 разных местах)

**Наш подход: Living Documentation**  
Документы обновляются ВМЕСТЕ с кодом, а не "когда-нибудь потом".

Стратегии обработки команд игрока.

**Для:** Детерминированные действия

**Для:** Сложная физика  
**Примеры:** опрокинуть стол  
**Стоимость:** ~0.002₽  
**Время:** 1000-2000ms

## 🔄 Workflow: Как Обновлять Документацию

### Ежедневно

1. **Утро:** Открыть `CURRENT_SPRINT.md`, выбрать задачу
2. **Вечер:** Отметить прогресс, обновить дневник

### После Каждого Коммита

Если изменения значительные:
- Обновить компонентный README (например, `services/README.md`)

### После Завершения Задачи

1. Отметить в `CURRENT_SPRINT.md`
2. Если задача связана с архитектурой → добавить ADR в `ARCHITECTURE_DECISION.md`

### После Завершения Спринта

1. **Закрыть спринт:**
   - Скопировать `CURRENT_SPRINT.md` → `DONE.md`
   - Написать ретроспективу

2. **Обновить стратегические документы:**
   - `MASTER_PLAN.md` → обновить метрики
   - `Technical_Design_Document.md` → обновить статусы
   - `BACKLOG.md` → пересмотреть приоритеты

3. **Создать новый спринт:**
   - Скопировать шаблон в `CURRENT_SPRINT.md`
   - Заполнить задачами из `BACKLOG.md`

## 🚨 Критические Правила

### ❌ НЕ ДЕЛАЙ

1. **Не откладывай обновление документации "на потом"**
   - Это "потом" никогда не наступит

2. **Не копируй код в документы**
   - Код изменится, документация устареет
   - Лучше: ссылки на файлы + краткое описание

3. **Не дублируй информацию**
   - Одна правда в одном месте
   - Используй ссылки между документами

4. **Не пиши "войну и мир"**
   - Краткость — сестра таланта
   - Лучше короткий и актуальный документ, чем длинный и заброшенный

### ✅ ДЕЛАЙ

1. **Обновляй документы ВМЕСТЕ с кодом**
   - Рефакторинг → обнови README
   - Новое решение → добавь ADR

2. **Используй чек-листы**
   - Наглядность прогресса
   - Мотивация (приятно ставить галочки)

3. **Пиши для себя в будущем**
   - Через 3 месяца ты забудешь, почему выбрал это решение

4. **Делай ретроспективы**
   - Что пошло хорошо?
   - Что улучшить в следующем спринте?

## 📊 Метрики Качества Документации

Хорошая документация соответствует критериям:

- ✅ **Актуальность:** Обновлялась < 1 месяца назад
- ✅ **Полнота:** Отвечает на вопросы "что, зачем, как"
- ✅ **Навигация:** Легко найти нужный документ
- ✅ **Консистентность:** Документы не противоречат друг другу
- ✅ **Действенность:** Помогает в реальной работе

**Самопроверка:**
> Если новый разработчик сможет понять архитектуру за 1 час чтения — документация хороша.
